# ADR-0032: Delphi-qualified Object Pascal discovery and package inventory

- Status: Accepted
- Date: 2026-08-01
- Scope: Delphi/Object Pascal in ADR-0020 wave N2; discovery/configuration only
- Refines: ADR-0020 and ADR-0030
- Related: `docs/specifications/indexing-pipeline.md`,
  `docs/specifications/unknowns.md`, and
  `docs/reports/language-support/delphi-object-pascal-completion-review.md`

## Context

`.pas` alone does not identify a single Object Pascal dialect. Delphi and Free
Pascal/Lazarus share source suffixes but have distinct project, package,
compiler, and semantic models. Treating a `.pas` file as proof of either
dialect would violate ADR-0020's dialect-first gate.

Embarcadero's official RAD Studio documentation provides a bounded Delphi
authority: `.pas`, `.dpr`, and `.dpk` are Delphi source forms; `.dproj` is the
IDE's Delphi project file; RAD Studio's project files are XML-based MSBuild;
and the Runtime Packages option is a semicolon-separated project list whose
entries may also be added automatically. That evidence supports inventory and
a conservative static runtime-package list. It does not prove an evaluated
configuration or direct/transitive package relationships.

The Free Pascal/Lazarus primary-source audit found `.lpi` examples containing
`RequiredPackages`, but did not establish a versioned normative `.lpi`/`.lpk`
format and directness/evaluation contract sufficient for the same production
parser. The first slice therefore chooses Delphi and leaves `.pp`, `.lpr`,
`.lpi`, and `.lpk` unsupported. It does not equate Lazarus packages with Delphi
runtime packages.

Primary format evidence reviewed for this decision:

- Embarcadero, [File Extensions of Files Generated by RAD Studio](https://docwiki.embarcadero.com/RADStudio/Alexandria/en/File_Extensions_of_Files_Generated_by_RAD_Studio), defines `.pas`, `.dpr`, `.dpk`, and `.dproj` roles;
- Embarcadero, [MSBuild](https://docwiki.embarcadero.com/RADStudio/Florence/en/MSBuild_Overview), identifies `.dproj` as the Delphi MSBuild project and describes XML items, properties, tasks, and targets;
- Embarcadero, [Runtime Packages (Options)](https://docwiki.embarcadero.com/RADStudio/Sydney/en/Runtime_Packages_%28Options%29) and [Loading Packages in an Application](https://docwiki.embarcadero.com/RADStudio/Athens/en/Loading_Packages_in_an_Application), define the project runtime-package list, semicolon syntax, omitted extensions/version suffixes, and automatically added packages; and
- Embarcadero, [Understanding the Structure of a Package](https://docwiki.embarcadero.com/RADStudio/en/Understanding_the_Structure_of_a_Package), defines `.dpk` `requires` relationships. That source format remains unread in this source-free slice.

## Decision

### D1. Source inventory is generic; configuration evidence is Delphi-specific

The stable source token is `object-pascal` for exact lowercase `.pas`, `.dpr`,
and `.dpk`. The generic token is deliberate: a `.pas` filename does not prove
Delphi versus Free Pascal. Exact `.dpr` and `.dpk` shapes are accepted within
the same source-free inventory but create no dialect or package semantics.

The stable config token is `delphi-config` for exact lowercase `.dproj`. This
is the only dialect-qualified configuration in the slice. `.pp`, `.lpr`,
`.lpi`, and `.lpk` remain unsupported and must not fall through to Delphi.
Exact `__history` and `__recovery` components are Object-Pascal/Delphi-only
exclusions; unrelated-language files below those names remain discoverable.

### D2. All Object Pascal source remains unread

`object-pascal` files persist only normalized repo-relative path, raw-byte
SHA-256, byte size, and token. Full and incremental indexing route `.pas`,
`.dpr`, and `.dpk` around the source store and parser. In particular, the
official `.dpk` `requires` clause is not read in this source-free slice.

RepoGrammar never invokes Delphi, `dcc32`, `dcc64`, RAD Studio, MSBuild, Free
Pascal, `fpc`, Lazarus, package compilation, package loading, project targets,
build events, tests, repository executables, child processes, or network
operations.

### D3. `.dproj` admits only literal runtime-package entries

An exact `.dproj` uses the same RepoGrammar-owned bounded XML reader and safety
limits as ADR-0031. DTDs, external/custom entities, malformed nesting,
duplicate attributes, and over-limit input fail closed. No schema, import,
property, condition, task, target, or compiler option is evaluated.

The parser creates one `delphi-config` `project_config` unit. It inventories
only bounded literal semicolon-separated names found in an exact
`DCC_UsePackage` property that is a direct child of a direct-root
`PropertyGroup`. Property/item expressions and entries containing paths or
compiled `.bpl`/`.dcp` suffixes are omitted. Names are deduplicated
case-insensitively.

Each admitted ADR-0030 row uses ecosystem `delphi_package`, evidence
`manifest_declared`, runtime scope, directness `unknown`, and no version.
Directness is deliberately unknown because the official project list may
contain authored choices, automatically added runtime packages, and packages
whose own requirements are represented elsewhere. A static property value
does not prove installation, transitive closure, platform/configuration
selection, package authenticity, loadability, buildability, or runtime use.

Imports, conditions, property chains, unsupported entries, malformed XML, and
resource overflow emit source-free `delphi_dependency_inventory` uncertainty.
Every nonempty package result also carries the explicit directness UNKNOWN.
Safe literal rows survive independently of omitted dynamic values.

### D4. Delphi and Free Pascal are never equated

The evidence ladder is:

1. primary inventory evidence: exact path/hash/size and `object-pascal` or
   `delphi-config` token;
2. primary static Delphi package evidence: a literal accepted
   `DCC_UsePackage` entry in supplied `.dproj` bytes;
3. diagnostic evidence: scoped typed UNKNOWN for configuration evaluation,
   directness, or omitted input;
4. forbidden evidence: `.pas` as a dialect oracle, `.lpi`/`.lpk` interpreted as
   `.dproj`, package presence as library behavior, or build/runtime output.

The Delphi/Object Pascal lane remains `discovered_only` and unsupported. There
is no source frontend, unified source IR, provider, framework role, family,
readiness promotion, or support claim. Source-only repositories are
`file_manifest_only`; an admitted `.dproj` creates a project-config unit and is
`syntax_only_code_units`.

### D5. Limits, tests, and follow-up

The XML and 2,000-identity dependency limits are the same as ADR-0031, with
exact-limit success and typed plus-one failure. Shared discovery ceilings,
symlink refusal, and the still-open ADR-0023 concurrent replacement gap are
unchanged.

Required tests cover source/config token separation, exact case, Free Pascal
non-admission, normalized paths, language-specific history/recovery exclusions,
binary source, source-store/parser bypass, DTD/entity refusal, property/
condition/import handling, invalid package values, exact/plus-one limits,
persistence/copy-forward/replacement/removal, source-free CLI output and mode,
unknown directness, and zero families.

A later Free Pascal/Lazarus lane requires its own evidence-pinned ADR for exact
`.lpi`/`.lpk` versions, package identity/directness, project selection, and
compiler mode. Delphi source analysis likewise requires a separately qualified
version-profiled frontend and cannot reuse an FPC parser as an unqualified
semantic oracle.

## Consequences

- Object Pascal source becomes visible without pretending path shape selects a
  dialect.
- Exact Delphi project metadata can supply bounded runtime-package inventory
  without executing proprietary or open-source toolchains.
- Free Pascal/Lazarus remains an explicit UNKNOWN/deferred boundary rather than
  being silently misclassified.
- The new lane remains incomplete and cannot contribute family evidence.
